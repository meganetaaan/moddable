# 第13章 なぜ xs なのか

## 13.1 `xs` を選ぶ価値

本書をここまで読んで、「`xs` は制約が多く、考えることも多い」と感じたかもしれません。それは正しい感想です。しかし、その制約は欠点ではなく、対象領域に正面から最適化した結果でもあります。

`xs` を選ぶ価値は、次の三つに集約できます。

1. ECMAScript の表現力を、非常に小さなマシンへ持ち込めること
2. build time、ROM、freeze、strip を通じて、実行環境をプロファイルできること
3. JavaScript と C の境界が薄く、組み込み向けの責務分担を作りやすいこと

## 13.2 `xs` が向いている状況

| 状況 | なぜ向いているか |
| --- | --- |
| RAM / flash が厳しい MCU を使う | preload、ROM 常駐、strip が効きます |
| 起動時間を短くしたい | build time 前倒しの恩恵が大きいです |
| アプリごとに言語機能を絞りたい | strip で engine profile を作れます |
| ドライバは native、ロジックは JS にしたい | `XS in C` と Native API が扱いやすいです |
| mod や compartment で拡張性も欲しい | sandbox と machine 分離の選択肢があります |

## 13.3 `xs` が向かない状況

逆に、次のような状況では `xs` は第一候補ではありません。

- 実行時動的コード生成が本質的に必要です
- 巨大な一般 purpose runtime と豊富な標準ライブラリが欲しいです
- JIT によるピーク計算性能が支配的です
- メモリ制約より、既存サーバ資産との完全互換や npm 依存の互換性が重要です
- 組み込み側ではなく、Web プラットフォームそのものを前提にしています

つまり `xs` は「どこでも動く JavaScript」ではなく、「制約を設計可能にする JavaScript」です。

## 13.4 他の選択肢との違い

細かな runtime 比較は対象や時期で変わりますが、判断軸はかなり安定しています。

| 判断軸 | `xs` の強み | 留意点 |
| --- | --- | --- |
| RAM / ROM 最適化 | 非常に強いです | build 設計と manifest 理解が必要です |
| 起動時間 | preload により強いです | pure / impure 分離が前提です |
| 言語互換性 | ECMAScript へ高い準拠を目指します | `Intl` など非対象領域があります |
| ネイティブ連携 | 非常に強いです | C 側 lifetime 設計が必要です |
| Web 互換 API | 目的ではありません | DOM / browser API はありません |

## 13.5 チームに求められる姿勢

`xs` を使うチームには、次の姿勢が必要です。

- manifest をコードと同じ重みでレビューする
- 実測値をチームで共有する
- pure / impure の境界を意識して module を切る
- C を怖がらず、しかし安易にも増やさない
- 実機検証を開発フローへ組み込む

逆に、「JavaScript だから何とかなる」「メモリは最後に調整する」という文化だと、`xs` の良さは出ません。

## 13.6 `xs` を選ぶ問い

プロジェクト開始時に、次の問いへ Yes が多いなら `xs` は有力です。

1. 起動時間と RAM が主要な制約ですか
2. pure module と実機依存コードを分けられますか
3. manifest や build 設計をレビュー文化に載せられますか
4. ドライバやホットパスは C で持っても構いませんか
5. 実機計測を継続できますか

逆に、No が多いなら、別の runtime や別の技術スタックを検討した方が健全です。

## 13.7 この章のまとめ

1. `xs` の価値は、小さな JavaScript ではなく、制約を設計可能にする JavaScript だという点です
2. preload、freeze、strip、`XS in C` がその中核です
3. `xs` は万能ではなく、動的性や汎用性より予測可能性を優先する場面で強いです
4. 適切に使うには、チーム側も build と実機計測を設計対象として受け入れる必要があります
