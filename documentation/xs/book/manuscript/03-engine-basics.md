# 第2章 JavaScript エンジンの共通モデル

`xs` の個性を理解するには、まず JavaScript エンジン一般の共通部分を押さえる必要があります。ここが曖昧なまま `preload` や Compartment の話に入ると、「特別な魔法」のように見えてしまいます。実際には、`xs` はエンジン一般の仕組みを持った上で、組み込み向けに取捨選択と前倒しを進めています。

## 2.1 JavaScript エンジンは三層に分けて考える

まずは全体像を整理します。ほとんどの JavaScript エンジンは、次の三層に分けて考えると理解しやすいです。

| 層 | 役割 | 代表的な話題 |
| --- | --- | --- |
| コンパイラ層 | ソースを内部表現へ変換する | 字句解析、構文解析、スコープ解決、バイトコード生成 |
| ランタイム層 | 値やオブジェクトを実際に扱う | スタック、ヒープ、関数呼び出し、例外、モジュール、Promise、GC |
| ホスト層 | 言語外の世界を提供する | ファイル、ネットワーク、タイマ、画面、デバイス、デバッガ |

ブラウザでは DOM や Web APIs、Node.js では libuv と多数の組み込みモジュールがホスト層に相当します。`xs` でも同様に、エンジン本体は汎用の ECMAScript 機能を実装し、デバイス I/O やネットワーク、スレッド、画面はホストが提供します。

## 2.2 コンパイルの流れ

JavaScript は動的言語ですが、だからといって「毎回その場で全部考える」わけではありません。一般的なエンジンは、概ね次の段階を踏みます。

1. ソースコードを読みます。
2. 字句解析してトークン列にします。
3. 構文解析してプログラム構造を把握します。
4. 変数やスコープを解決します。
5. 実行しやすい内部表現を作ります。
6. その内部表現をインタプリタや JIT で実行します。

この内部表現が AST のままか、バイトコードか、あるいはさらに低レベルな中間表現かはエンジンごとに違います。しかし、「ソースの構造を前もって理解し、実行時の探索を減らす」という方向性は共通です。

`xs` でもこの原理は同じです。違うのは、その結果をどこまで build 時に前倒しできるか、という点です。

## 2.3 スタックとヒープ

ランタイム層では、スタックとヒープの区別が非常に重要です。

- スタックは、関数呼び出しや式評価のための短命な作業領域です。
- ヒープは、オブジェクト、配列、クロージャ、文字列、バッファのような長命データを置く領域です。

Web 向けエンジンでも `xs` でも、この基本構造は共通です。ただし `xs` では、スタックやヒープの大きさを manifest や creation パラメータで露骨に意識することになります。これは一般論ではなく `xs` 固有の実務感覚ですが、土台となるモデル自体は普遍です。

## 2.4 スコープとクロージャ

JavaScript は lexical scope を持つ言語です。つまり、識別子がどこを指すかはソース構造で決まります。エンジンは、関数のたびに「この名前はローカル変数か、外側のクロージャか、グローバルか」を解決します。

ここで重要なのは、実行時に毎回文字列探索をしているわけではないことです。多くのエンジンでは、コンパイル時に識別子を分類し、実行時はインデックスや固定された参照を使います。

これにより、次のような差が生まれます。

- ローカル変数アクセスは安いです。
- 深いクロージャの捕捉は、それなりのコストがあります。
- `eval` や動的な名前解決は最適化を難しくします。

この事情は `xs` でも同じです。むしろ RAM 制約が厳しいぶん、不要な動的性質を持ち込まない設計がより重要になります。

## 2.5 モジュール

ES Modules は、ファイル分割の仕組みであり、同時にエンジンにとっては依存グラフ管理の仕組みでもあります。エンジンは、どのモジュールが何を import しているか、いつ評価されたか、同じ specifier はどの実体に対応するかを管理しなければなりません。

モジュールでは次の論点が出てきます。

- specifier 解決
- 依存順序の決定
- 循環依存の扱い
- live binding の管理
- 初回評価と再利用

`xs` の Compartment や Mods を理解する上でも、モジュールマップという発想は基礎になります。

## 2.6 Promise とジョブキュー

Promise もまた、エンジン一般の仕組みです。重要なのは、`then` や `await` の継続が即時実行されるのではなく、ジョブキューへ積まれ、ホストが適切なタイミングで流す点です。

ブラウザでは event loop の microtask queue という言い方に慣れていると思います。`xs` でも概念は同じですが、どこでキューを回し、どこまでホストが責任を持つかは実装とホスト構成に依存します。この違いは後の章で詳しく扱います。

## 2.7 ガベージコレクション

オブジェクトを自動回収する仕組みが GC です。アルゴリズムには様々な流儀があります。

- mark-sweep
- copying
- generational
- incremental
- concurrent
- compacting

Web 向け巨大エンジンでは、停止時間とスループットの両立のためにかなり複雑な戦略が使われます。`xs` では、ROM/RAM 制約、実装サイズ、補助メタデータの大きさ、MMU の有無、断片化耐性が優先されます。ここも一般論と `xs` 固有の選択を分けて考えるべき点です。

## 2.8 ホスト環境は言語そのものではない

ECMAScript 仕様が定義するのは言語本体です。画面描画、ネットワーク接続、タイマ、GPIO、ストレージ、デバッガ接続は別です。つまり、アプリから見えている「JavaScript でできること」のかなりの部分は、ホストが与えているにすぎません。

この区別は `xs` で特に重要です。たとえば、`pins/digital` のような API は ECMAScript の一部ではなく、Moddable ホストが提供しているものです。同じ JavaScript を書いていても、そこにある能力はホスト次第です。

## 2.10 Web エンジニア向けの再確認

この章で持ち帰ってほしいのは、次の三点です。

1. `xs` を学ぶことは、JavaScript エンジン一般の仕組みを学ぶことでもあります。
2. ただし `xs` は、その一般論の上に「組み込み向けの極端な前倒し」を積んでいます。
3. したがって、Web の経験は無駄ではありませんが、前提の優先順位を入れ替える必要があります。

次章では、その前倒しを実現する Moddable のツールチェーン全体像を見ていきます。
