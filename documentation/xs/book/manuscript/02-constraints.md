# 第1章 Web エンジニアの前提をいったん壊す

Web エンジニアが `xs` に触れて最初に驚くのは、JavaScript そのものよりも、JavaScript を取り巻く前提条件です。ブラウザや Node.js では、数十 MB から数 GB のメモリ、比較的高速な CPU、OS による保護、豊富なデバッグ支援を当たり前として使っています。`xs` の主戦場となる MCU では、その前提が成立しません。

## 1.1 何が違うのか

Web 側では、次のような発想が自然です。

- ソースコードは実行時に読むものです。
- エンジンは大きくても構いません。
- 起動時に初期化コストを払っても、多くの場合は許容されます。
- 一時的なメモリ増加は GC が何とかしてくれる、と期待しがちです。
- `eval` や `Function`、動的 import、巨大な組み込みライブラリは便利なので残しやすいです。

組み込みでは、これらがそのまま逆転します。

- ソースを毎回読む余裕がないので、バイトコード化や preload が重要になります。
- 使わない言語機能の ROM コストを削るため、strip が意味を持ちます。
- 起動時間は UX だけでなく、電力、再起動耐性、ウォッチドッグ設計にも効きます。
- RAM 不足は遅くなるのではなく、失敗や再起動に直結します。
- 動的変更を可能にするメタデータですら、数バイト単位で負担になります。

ここで重要なのは、「小さいデバイスだから全部我慢する」という話ではないことです。むしろ、どこに柔軟性を残し、どこを固定化するかの境界設計がはっきり要求される、という話です。

## 1.2 制約は量ではなく種類の違いでもある

Web のサーバやデスクトップでは、失敗しても OS がかなりの部分を吸収します。仮想メモリ、プロセス分離、ログ収集、再起動機構、監視基盤があり、最悪でもプロセスが落ちる程度で済むことが多いです。

一方 MCU では、次のような事情があります。

- OS が無いか、あっても非常に薄いです。
- メモリ不足時の退避先がありません。
- ドライバとアプリが密接に結び付きやすいです。
- 再起動コストがそのままユーザー体験や外部機器の状態に跳ねます。
- 電池駆動では、起動や通信のたびに消費電力が問題になります。

このため、平均性能よりも「最悪時に何が起きるか」「起動時に何が確定しているか」「RAM 消費がどこまで予測できるか」が重要になります。`xs` がビルド時前倒しを強く推すのは、このためです。

## 1.3 Browser、Node.js、xs を同じ JavaScript として見すぎない

次の表は、Web 開発者が暗黙に期待しがちな挙動を、`xs` 側から見直したものです。

| テーマ | Browser / Node.js の感覚 | xs での見直し |
| --- | --- | --- |
| コード読込 | 実行時に source を読む | 基本は build 時に `.xsb` や frozen preparation にする |
| 起動 | 遅くても許容しやすい | 可能な限り preload で前倒しする |
| メモリ | 足りなければ増設やスワップの余地がある | 足りなければ即座に設計を見直す必要がある |
| 言語機能 | 便利なら残す | ROM 予算に応じて strip する |
| デバッグ | CPU やメモリに余裕がある | 観測自体のコストも意識する |
| 拡張 | 動的ロードは比較的自由 | Mods や Compartment を使っても予算管理が必要 |

`xs` を理解する第一歩は、JavaScript が同じでも、ランタイム設計の優先順位が違うと認めることです。

## 1.4 失敗のしかたが違う

Web のコードでは、アンチパターンが性能劣化として現れることが多いです。たとえば、不要なオブジェクト生成が多いと GC が増え、レスポンスが少し悪くなります。しかし `xs` では、同じような書き方が「起動できない」「接続直後に落ちる」「Worker を増やしたら突然不安定になる」という形で現れます。

よくある原因は次のとおりです。

- preload 可能な初期化を実行時に残している
- 凍結できるデータや prototype を凍結していない
- 動的なキーや大きなメッセージを無造作に増やしている
- Worker に main と同じ大きさのメモリを与えてしまっている
- Mods や Compartment を導入したのに key 予算や strip 方針を調整していない

これらは API の使い方ミスというより、エンジンの動作原理への理解不足です。本書が内部構造から入るのはそのためです。

## 1.5 組み込み JavaScript をどう捉えるべきか

本書では、組み込み JavaScript を「Web より不自由な世界」としては扱いません。むしろ、次のように捉えます。

- エンジン内部の理解が、そのままアプリ設計品質に跳ね返る世界です。
- ビルド設定、言語設計、データ設計、ホスト境界が強く結び付く世界です。
- API 選択だけではなく、起動時に何を確定させるかが設計の中心になる世界です。

<code>xs</code> は「Web の JavaScript をそのまま小さくしたもの」ではありません。制約を前提に、ビルドと実行の境界を設計し直した JavaScript ランタイムです。

## 1.6 先に持っておくべき実務感覚

本書の残りを読む前に、次の感覚だけは先に持っておくと理解が速くなります。

1. 起動時に必要なものは、できるだけ build 時に作っておきます。
2. 変わらないものは、できるだけ freeze して ROM に押し込みます。
3. JavaScript だけで完結させることより、JS と C の境界を適切に切ることが重要です。
4. メモリ不足は偶然ではなく、だいたい設計のシグナルです。
5. 観測なしで最適化しません。`xsbug` の計測値を見て判断します。

この五つは、本書全体を通じて繰り返し確認していきます。
